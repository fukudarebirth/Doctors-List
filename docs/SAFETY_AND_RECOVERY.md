# 本番追記と復旧：次段階の設計

現在の実装は第1〜4段階で、OAuth権限も読み取り専用です。`apply` / 承認 / Google書き込みコマンドはありません。
追記案には値・開始行・行高20pxの要件を出しますが、実際の書式継承・保存検証は未実装です。
本書は今すぐ本番更新を実行する手順ではなく、第5〜6段階の受入基準です。

1. 全シートの最新メタデータ・値・数式・セル書式・入力規則・列幅・行高を取得し、人物シートの分類を確認。
2. 追加・除外・保留と具体的差分を提示。確認対象の正本ハッシュ、候補ハッシュ、追記日、操作IDを承認へ結び付ける。
3. ユーザーが対象差分を明示承認。一般的な開発依頼や引用「あ」は承認にしない。
4. 単一の書き込み担当を確保し、直前に全シートを再取得。正本・候補・日付が変われば承認を無効化、再評価。
5. 正本の値・数式・書式をバックアップし、リポジトリ外への保存・再読込を検証。操作ジャーナルを先に永続化。
6. 実データ最終行直下だけへA〜Gを追記。Bは未確認なら空欄。JST同日の日付は1回。既存値はRAW相当で保持し、数式注入を避ける。
7. 追加範囲だけ既存の書式・入力規則を継承、行高20px。列幅、既存行、タイムゾーンを変更しない。
8. 全シート再取得で予定値・連続行・既存データ・既存書式・新規行高・列幅・分類整合・重複・人数を検証。
9. 検証済み保存結果からだけ除外マスターを差分更新し、保存を再確認。保存済みの追加人数を報告。

Google Sheets APIの通常の読み取り→書き込みは厳密な比較更新・排他を保証しません。ローカルロックや直前のハッシュだけでも他PC・手動編集との競合を防げません。
書き込み時間中は担当者1名・実行プロセス1つとし、対象シートの他編集を停止する運用が必要です。この制約が満たせなければ自動更新を許可しません。

## エラー時

- OAuth / 通信 / シート取得エラー: 古いキャッシュへ自動退避しない。今回の判定を停止して認証・通信・構成を確認後に読み取りをやり直す。
- 未分類シート / 列変更: 本文を調べ人物シートか判断し、対応する列マッピングの実装・検証をしてから進める。
- マスターJSONが未知形式: 原本を保持。個人情報なしのスキーマだけ確認し、対応表・変換処理を実装。古いマスター単体で未登録にしない。
- ローカルレポートやマスター保存失敗: 一時ファイル段階の失敗なら元ファイルを保持。成功表示がなければ出力を再読込しハッシュを照合。
- 将来のGoogle書き込みタイムアウト: 成否不明として停止。ジャーナルの予定範囲・値・操作IDと現在のシートを照合。無条件リトライ禁止。
- 全部保存済みなら再追記せず検証を再開。一部保存・他編集混在なら隔離して人が確認。自動削除・上書きロールバックをしない。

現在はGoogle書き込みがないため、何度Dry Runしても本番の二重登録は発生しません。将来の二重実行抑止・部分書き込み復旧は別途実API検証が必要です。
